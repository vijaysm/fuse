# The native mesh backend's remap halo

`fuse::native::NativeMeshBackend` (docs/dev/native-mesh.md) can report more than one rank -- a
distributed decomposition generated by `generate_native_mesh(spec, rank, num_ranks)` or built by
`fuse::partition::repartition` -- with no MOAB in the build at all. `fuse::build_weights`'s conservative
supermesh builder (`build_supermesh_weights`, `src/backend/supermesh.cpp`) intersects the cells a rank
HOLDS, and on a partitioned read that is correct exactly when the source mesh carries a REMAP HALO: the
off-rank source cells that overlap this rank's target cells, adopted as ordinary non-owned local
entities. This is the same `A-PARTITIONED` gap `MoabMeshBackend::adopt_remap_halo`/`build_remap_halo`
close for MOAB (`remap_plan.hpp`'s own header), closed here for the native backend, whose covering-set
construction is PLANAR/VOLUMETRIC rather than spherical.

## The construction

Each rank forms the axis-aligned bounding box of every one of its OWNED target cells (per cell, not one
union box for the whole slab -- more selective, and no more expensive at the cell counts this track
targets). Every rank's own boxes are gathered onto every other rank (`MPI_Allgather` for counts, then
`MPI_Allgatherv` for the flattened `(lo, hi)` doubles -- the same two-phase shape
`resolve_vertex_ownership`, native_migration.cpp, already uses for a variable-length allgather). A rank's
OWNED source cell then travels, as a COPY (never a move: its owner never changes), to every OTHER rank
whose gathered target boxes it overlaps.

**Planar and volumetric are the SAME construction.** A box-box overlap test in three coordinates does
not care which topological dimension the cells it bounds are; a planar mesh's boxes simply have
`lo[2] == hi[2] == 0` (every vertex's z is 0 by construction, `native_generators.cpp`). No dimension
branch exists anywhere in `src/backend/native_halo.cpp`'s own geometry.

**A touch is not an overlap.** Two boxes that only share a face -- the common case at an EXACTLY aligned
partition boundary, which this track's own test fixture hits deliberately -- have a true geometric
intersection of measure zero: real cells are contained in their bounding boxes, so a zero-measure box
intersection proves the real cells cannot overlap with positive area either, regardless of shape.
`boxes_overlap`'s `kTouchTol` margin excludes an exact touch, but ONLY on an axis where at least one of
the two boxes has real extent -- applying it unconditionally breaks every planar pair outright, because
z is `lo == hi == 0` for EVERY cell of a 2D mesh, which is the mesh's own embedding, not a boundary
artifact. (Measured during development: the unguarded version adopted zero cells everywhere, not just at
an aligned boundary -- see `native-halo-boxes-overlap-degenerate-axis-tolerance`,
`build-evidence/mutations/native-mesh.toml`.)

## The wire format and adoption

`pack_halo_cells` (native_halo.cpp) serializes a copied cell exactly as `native_migration.cpp`'s own
per-cell closure does (global id, `CellType`, vertex closure by global id + coordinates, and a
Polyhedron's face CSR) PLUS two leading fields a migrated cell never needs: the OWNER's rank (always the
sender, since a halo cell is copied, never moved) and that cell's own position among the sender's OWNED
cells, ascending local-index order (`owned_block_index`) -- the "owned block" position
`fuse::linalg::DistVector`/`GhostPattern` (`fuse/linalg/comm.hpp`) already use for exactly this purpose.
The byte buffers travel through the EXISTING `fuse::native::exchange_migration_buffers` (an
`MPI_Alltoallv`, generic over byte payloads); no new MPI collective was added for the exchange itself.

`merge_halo_cells` rebuilds `source`'s MeshArrays from scratch through `NativeMeshBuilder`: every
EXISTING cell and vertex, copied verbatim (ownership, owner rank, and -- for a cell already adopted by an
earlier call for a DIFFERENT target -- its non-owned status all preserved exactly), THEN every NEW cell
found in the incoming buffers whose global id is not already held (the same "skip a duplicate" rule
`MoabMeshBackend::adopt_remap_halo` documents), appended NON-OWNED with the ORIGINAL sender as
`cell_owner_of`, strictly after every existing cell. `NativeMeshView::create_from_host` then finalizes
the combined arrays -- the same tested per-cell-shape geometry (simplex decomposition, centroid,
measure) every other construction path uses, rather than a second, hand-written incremental-append
implementation of it.

**Deviation from the MOAB backend's pointer-stability contract.** `mesh_view.hpp` promises a `MeshView*`
stays valid "until the backend is destroyed or moved from"; `MoabMeshBackend::adopt_remap_halo` honours
this by growing MOAB's own entity set in place. `NativeMeshBackend::commit_remap_halo` instead REPLACES
the stored `unique_ptr<NativeMeshView>` at the same `(MeshId, ComponentId)` key with the freshly rebuilt
one -- the standing priority (robustness over efficiency) favoured reusing `create_from_host`'s tested
geometry over a second, hand-written incremental append. A caller must not cache a raw `MeshView*`
obtained before `build_remap_halo` runs and keep using it afterward; `remap_plan.hpp`'s own "ORDER
MATTERS" discipline (halo before anything sizes a buffer) already requires this of every caller, and
every path this library drives itself (`resolve()`/`supermesh_side()` in `intx_weights.cpp`) re-fetches
the view by key, never holds one across a halo build.

## The field-value contract: `remap_halo_pattern`

`NativeMeshBackend::remap_halo_pattern(source, target, dim)` returns a `fuse::linalg::GhostPattern` --
`owner_rank`/`remote_local_index`, one entry per adopted cell, in the order they were appended (after
every owned cell) -- so a caller fills the adopted cells' FIELD values with
`fuse::linalg::make_mpi_exchanger(comm, pattern, owned_n)` before `apply_weights`, exactly the sequence
`remap_plan.hpp`'s own header states: `build_remap_halo -> build_weights -> exchange -> apply_weights`.
`has_remap_halo`/`remap_halo_pattern`'s presence in the backend's bookkeeping -- not the pattern's size --
is "was a halo built"; an empty pattern (two aligned partitions, nothing needed to cross) is a
legitimately built, zero-cell answer.

## What is conservative here, and what a first-order remap is NOT

Row-sum-1 (checked to round-off by every test in this track) reproduces a CONSTANT field exactly, and the
column-mass sum -- a source cell's measure, accounted once on its owner's own weights and once on every
halo copy's, summed by global id -- conserves the integral to round-off. Neither claims exact
reproduction of a LINEAR field: a piecewise-constant (first-order) remap's reproduction error for a
non-constant field is bounded by that field's own variation across the coarsest source cell that can
fully contain a target cell (a Lipschitz bound, not a discretization bug), and
`test/backend/native_halo_test.cpp`'s own fixture measures it explicitly rather than asserting round-off
where none is owed.

## What is tested where

- `test/backend/native_halo_test.cpp` (tier 0, actually run here): the pure pieces (`cell_box`,
  `covering_set_destinations`, `owned_block_index`, `pack_halo_cells`, `merge_halo_cells`) against
  hand-built boxes and a small 2-rank round trip; the 16x16 (source) / 24x24 (target) quad-grid pair,
  slab-decomposed by row over the SAME ranks, at 2 ranks (the row split aligns exactly at y = 0.5: zero
  cells adopted) and 3 ranks (6/5/5 vs 8/8/8: misaligned, checked against an independently computed
  brute-force oracle); `fuse::build_weights` through the real entry point after the halo is installed via
  the real `commit_remap_halo` seam, with row-sum, linear-field, and cross-rank conservative column-mass
  checks; and `build_native_remap_halo`'s own no-op short-circuits (one rank, no communicator, identity
  source/target), which are the only cases this file can call the REAL orchestration function, because
  they return before any MPI symbol is touched.
- `test/parallel/native_halo_mpi_test.cpp` (tier 1, built but not run in this sandbox -- MPI cannot
  start here at all, docs/dev/testing.md): the same scenario under a REAL `MPI_COMM_WORLD`, with
  `build_native_remap_halo` performing its own real collectives and
  `fuse::linalg::make_mpi_exchanger` (not an in-process stand-in) filling the adopted cells' field
  values. Registered at `RANKS 2 3` (test/CMakeLists.txt); `parallel.native_halo_mpi.{2,3}` both
  passed on the host 2026-10-10 (0.37 s, 0.08 s).
- `build-evidence/mutations/native-mesh.toml`'s `native-halo-*` rows: hand-proven against a scratch copy
  (apply, rebuild, run `fuse_backend_native_halo_test` whole and unfiltered, record the exact
  pass/fail split, restore and `cmp` byte-identical).

## Device packing (Phase 2, "weight-builders" track)

`include/fuse/backend/native/mesh_pack_device.hpp` adds `fuse::native::device::pack_to<kHaloRecord,
Space>`, the Space-templated packing seam `docs/dev/device-resident-arcs.md`'s Phase 2 names. It
builds the IDENTICAL wire records `pack_for_migration`/`pack_halo_cells` do (`kHaloRecord` selects
which of the two), but reads `MeshArrays<Space>`'s own CSR connectivity directly rather than walking
`NativeMeshView` -- a host-only, validated view by design (`Result`/`Failure`/`fmt` are not
device-callable) -- so that on `Space == Kokkos::DefaultExecutionSpace::memory_space` the owned-block
numbering, every record's byte size, and the byte-level write all run as Kokkos kernels, with no host
round trip for the per-cell data. Verified byte-for-byte against the existing host packers on the same
generated meshes (quad and polyhedral), in both Host mode and Device mode (`test/backend/
native_mesh_pack_device_test.cpp`).

## Device merge decision (KNOWN_ISSUES D51, narrowed)

`include/fuse/backend/native/mesh_merge_device.hpp` adds `fuse::native::device::dedup_by_gid<Space>`:
the receiving side's MERGE DECISION itself -- "is this incoming global id already held, and if it is
genuinely new, which ONE of possibly several cross-sender copies is canonical" -- as Kokkos kernels on
`Space`, replacing the `std::unordered_map`/`std::unordered_set` membership test `merge_halo_cells`'s
cell dedup and `unpack_migrated_mesh`'s vertex dedup both make today. A sort-and-compact pass:
`Kokkos::Experimental::sort_by_key` the concatenation of the already-held gids and the incoming
candidates (carrying a signed tag that encodes both side and original position), then one
`Kokkos::parallel_scan` over the sorted order assigns every DISTINCT value one ascending slot, and an
`atomic_min` pass picks the lowest-original-index incoming copy as canonical for a slot no existing
entry claims -- the same "first occurrence in buffer order wins" rule the Host path already follows,
so Device mode never disagrees with what Host would keep for the same input order.
`O((E + N) log(E + N))` for the sort (the dominant term), `O(E + N)` for the rest. Verified against a
from-scratch `std::unordered_map`/`std::unordered_set` reference on gid sets built to exercise every
case the real wire traffic can produce (no overlap, incoming duplicates of an existing entry,
cross-sender duplicates among incoming, empty incoming, empty existing), in both Host mode and (when
this Kokkos has one) a Cuda/HIP/SYCL backend (`test/backend/native_mesh_merge_device_test.cpp`).

**Not yet done:** wiring this primitive into `merge_halo_cells`/`unpack_migrated_mesh` themselves.
Two gaps remain, both stated rather than assumed:

1. **Slot numbering.** `dedup_by_gid`'s output numbers the merged gid set ascending BY VALUE, not by
   the Host builders' own append-order convention (every existing vertex/cell keeps its original local
   index; new ones are appended in first-encounter order) -- a caller that needs byte-for-byte parity
   with the Host numbering adds one more renumbering pass (sketched in `mesh_merge_device.hpp`'s own
   header comment), not a second dedup algorithm.
2. **Record-boundary discovery.** The wire format's records are variable length with no byte-length
   prefix (`mesh_pack_device.hpp`'s own format), so locating each record's start offset in a received
   buffer -- the step before a flat gid array for `dedup_by_gid` even exists -- is only discoverable by
   walking the buffer; parallelizing that (or adding a length prefix so it CAN be parallelized) is a
   separate change neither this entry nor `dedup_by_gid` attempts.

So a Device-mode caller of `build_native_remap_halo`/`migrate` still needs a host round trip for the
full merge, but the DECISION at its core -- which this entry's own scope note (2026-10-13) named as
"the open piece," for lack of a device-friendly hash-set primitive -- is now implemented and tested.

## Open items

- The conservative column-mass-by-global-id check (a source cell's measure, summed across every rank
  holding a copy of it) is test-level bookkeeping in `native_halo_test.cpp`, not a library API; MOAB's
  own `accumulate_remap_halo` (the reverse exchange, built for exactly this audit) has no native
  counterpart. Nothing in this track's scope needs it at the library level yet -- `remap_halo_pattern`'s
  only documented purpose is the FORWARD fill before `apply_weights` -- but a future conservation-audit
  tool for the native backend would want one.
- `build_native_remap_halo` dispatches through `intx_weights.cpp`'s `build_remap_halo`/
  `build_weights_via_supermesh`, alongside the MOAB path, via `dynamic_cast`; a backend that is neither
  MOAB nor native and reports more than one rank is not covered by any E-REMAP-PARALLEL check in this
  tree (none exists yet that does).
