# Coupling an existing Fortran code

This page is for Fortran simulations that want to take part in a FUSE coupling: a code that owns its
time loop and drives FUSE through the `ffuse` module (a **participant**), or a solver packaged as a
shared library that FUSE loads and drives through the `ffuse_provider` module (a **provider
plugin**). It covers the build, both modules' public interfaces, complete examples, and the
workflows a Fortran code can take part in. The entry-by-entry contract is the participant ABI
described in [](c-abi.md), which applies here member for member; [](mixing-languages.md) compares
the ways codes in different languages can be combined.

`ffuse` and `ffuse_provider` are generated by `tools/gen-abi.py` from the same entry list
(`include/fuse/abi/entries.def`) as the C headers, so the module and the header cannot disagree.
Fortran does not get the C side's single-symbol table. Dereferencing a struct of function pointers
from Fortran is unpleasant, so the binding is a second library, `libfuse-abi-fortran`, exporting a
flat family of `bind(C)` symbols, `ffuse_<entry>`, each of which forwards to the C table at first
use. `libfuse-abi` itself still exports exactly one symbol, `fuse_coupler_abi`.

## A complete minimal participant

```fortran
program couple
  use, intrinsic :: iso_c_binding
  use ffuse
  implicit none

  type(fuse_ctx) :: ctx
  type(fuse_null) :: nothing
  type(fuse_context_out) :: made
  type(fuse_field_ref) :: heat_flux
  type(fuse_field_view) :: view
  type(fuse_ongoing) :: ongoing
  type(fuse_step_report) :: report
  real(c_double), target :: q(100)
  integer(c_int32_t) :: status

  status = fuse_create(ctx, nothing, made)      ! ctx%ptr must be null on entry
  ctx%ptr = made%ctx                            ! ... and holds the new context after

  status = fuse_load_graph(ctx, "coupling.yaml", nothing)   ! string overload

  status = fuse_field_handle(ctx, "fluid", "heat_flux", heat_flux)

  view%handle           = heat_flux%handle
  view%element_type     = FUSE_ELEMENT_F64
  view%memspace         = FUSE_MEMSPACE_HOST
  view%ownership        = FUSE_OWNERSHIP_OWNED
  view%components       = heat_flux%components
  view%count            = size(q, kind=c_int64_t)
  view%owned_count      = size(q, kind=c_int64_t)
  view%stride           = 1_c_int64_t
  view%component_stride = 1_c_int64_t
  view%data             = c_loc(q)              ! q must stay valid until fuse_destroy
  status = fuse_register_field(ctx, view, nothing)

  status = fuse_initialize(ctx, nothing, nothing)

  status = fuse_is_coupling_ongoing(ctx, nothing, ongoing)
  do while (ongoing%ongoing /= 0)
    status = fuse_begin_step(ctx, "fluid", report)   ! q's imports are current on return
    call advance_my_solver()
    status = fuse_end_step(ctx, "fluid", report)      ! q's exports are read here
    status = fuse_is_coupling_ongoing(ctx, nothing, ongoing)
  end do

  status = fuse_destroy(ctx, nothing, nothing)
end program couple
```

Every procedure has the shape `fuse_<entry>(ctx, in, out)`, matching the C side's
`fuse_status name(fuse_ctx* ctx, const IN* in, OUT* out)` member for member; `in`/`out` are
`fuse_null` variables where C passes `NULL`. The function result is the status, compared against the
`FUSE_OK` / `FUSE_ERR_*` parameters `ffuse` exports. This loop runs forever unless `fuse_setup` set
an end time; the real programs below bound their loops with a period count.

## Building and linking

`FUSE_ENABLE_FORTRAN` is `ON` by default. If CMake finds no Fortran compiler it turns the option off
with a message rather than failing to configure:

```sh
cmake -S . -B build -DFUSE_ENABLE_FORTRAN=ON
cmake --build build --target fuse-abi-fortran
```

The target `fuse-abi-fortran` (alias and exported name `fuse::abi-fortran`) is a static library
built from `fortran/ffuse.f90`, `fortran/ffuse_provider.f90` and the C shim
`fortran/fuse_fortran_shim.c`. The Fortran sources are compiled with
`-std=f2008 -Wall -Wextra -Werror -fimplicit-none`. The `.mod` files are written to
`<build>/fortran/mod` in the build tree and installed to `<prefix>/include/fuse-fortran`; both
directories are on the target's interface include path, so a consumer that links the target needs no
`-I` of its own.

A downstream Fortran project links **two** ABI libraries: `fuse::abi-fortran`, whose only undefined
symbol is `fuse_coupler_abi`, and the shared `fuse::abi` that defines it. It also needs `Threads`
(the shim uses `pthread_once`, a private dependency a static archive cannot carry) and the CXX
language enabled, because the installed package probes `OpenMP_CXX` for Kokkos. This is the
configuration the install test uses (`test/abi/fortran/install_consumer/CMakeLists.txt`):

```cmake
cmake_minimum_required(VERSION 3.24)
project(my_fortran_participant LANGUAGES Fortran CXX)

find_package(Threads REQUIRED)
find_package(fuse-coupler CONFIG REQUIRED)

add_executable(participant participant.f90)
target_link_libraries(participant PRIVATE fuse::abi-fortran fuse::abi)
```

:::{note}
Link the shared `fuse::abi`, not `fuse::abi-static`. The static variant does not carry the private
dependencies (yaml-cpp, r3d) an installed consumer needs at its final link, and the link fails with
undefined symbols.
:::

A Fortran provider plugin is a shared library linked the same way:

```cmake
add_library(my_provider SHARED my_provider.f90)
target_link_libraries(my_provider PRIVATE fuse::abi-fortran fuse::abi)
```

## The `ffuse` module

Everything below is `public` in `fortran/ffuse.f90`; everything else in the module is private.

### Parameters

All of kind `integer(c_int32_t)`, with the values of `fuse/abi/types.h`:

- `FUSE_OK`, `FUSE_ERR_INVALID`, `FUSE_ERR_NOTFOUND`, `FUSE_ERR_STATE`, `FUSE_ERR_RUNTIME`,
  `FUSE_ERR_UNSUPPORTED`, `FUSE_ERR_VERSION`
- `FUSE_ELEMENT_F64`, `FUSE_ELEMENT_I64`
- `FUSE_MEMSPACE_HOST`, `FUSE_MEMSPACE_DEVICE`
- `FUSE_OWNERSHIP_OWNED`, `FUSE_OWNERSHIP_GHOSTED`, `FUSE_OWNERSHIP_REPLICATED`
- `FUSE_CAP_DEVICE_FIELDS`, `FUSE_CAP_CHECKPOINT`, `FUSE_CAP_MPI`, `FUSE_CAP_MPI_CONNECT`,
  `FUSE_CAP_LOWFIVE`, `FUSE_CAP_YAML`, `FUSE_CAP_RESTART_FORM_B`
- `FUSE_ABI_VERSION`, `FUSE_ABI_MAX_STRUCT_SIZE`

### Derived types

`fuse_ctx` is the one type that is not `bind(C)`: a wrapper holding `type(c_ptr) :: ptr`, default
`c_null_ptr`. `fuse_create` requires it null on entry and `made%ctx` is assigned to it afterwards.

Every other type is `type, bind(C)` with the same name and the same members, in the same order, as
the C struct, and every member default-initialised to its documented default (`0`, `c_null_ptr`,
`fuse_exact_time(0, 1)`):

| Type | Used by |
|---|---|
| `fuse_exact_time` (`numerator`, `denominator`), `fuse_semantic_version` | value types, no `struct_size` |
| `fuse_null` | the empty `in`/`out` argument |
| `fuse_version_info`, `fuse_capability_set` | `fuse_version`, `fuse_capabilities` |
| `fuse_context_out` | `fuse_create` |
| `fuse_error` | `fuse_last_error` (struct form) |
| `fuse_graph_source`, `fuse_graph_sink` | `fuse_load_graph`, `fuse_save_graph` |
| `fuse_setup_options` | `fuse_setup` |
| `fuse_field_name`, `fuse_field_ref`, `fuse_field_view` | `fuse_field_handle`, `fuse_register_field`, `fuse_view_field` |
| `fuse_step_request`, `fuse_step_report` | `fuse_begin_step`, `fuse_end_step`, and a provider's `advance` |
| `fuse_ongoing`, `fuse_run_request` | `fuse_is_coupling_ongoing`, `fuse_run` |
| `fuse_base_communicator_info` | `fuse_base_communicator` |
| `fuse_field_spec`, `fuse_field_table`, `fuse_provider_instance` | a provider's `describe` and `create` |
| `fuse_restart_blob_sink`, `fuse_restart_blob_source` | a provider's `save_restart_blob` / `load_restart_blob` |

`C_SIZEOF` of each type equals the C `sizeof`, pinned by `test/abi/struct_sizes.golden` and the
`abi.fortran_sizes` test.

### Procedures

Every procedure is a function returning `integer(c_int32_t)` (the status) whose first argument is
`type(fuse_ctx), intent(in) :: ctx`. The `in` and `out` arguments are `intent(inout)` so the wrapper
can set `struct_size`; pass variables, not expressions.

| Procedure | `in` | `out` | Notes |
|---|---|---|---|
| `fuse_version(ctx, in, out)` | `fuse_null` | `fuse_version_info` | `ctx` may be a default (null) `fuse_ctx` |
| `fuse_capabilities(ctx, in, out)` | `fuse_null` | `fuse_capability_set` | likewise |
| `fuse_create(ctx, in, out)` | `fuse_null` | `fuse_context_out` | `ctx%ptr` must be null; then set `ctx%ptr = out%ctx` |
| `fuse_destroy(ctx, in, out)` | `fuse_null` | `fuse_null` | |
| `fuse_last_error(ctx, in, out)` | `fuse_null` | `fuse_error` | struct form; the string form is below |
| `fuse_load_graph(ctx, in, out)` | `fuse_graph_source` | `fuse_null` | struct form; the path form is below |
| `fuse_save_graph(ctx, in, out)` | `fuse_null` | `fuse_graph_sink` | query with `buffer = c_null_ptr`, then fill |
| `fuse_setup(ctx, in, out)` | `fuse_setup_options` | `fuse_null` | collective |
| `fuse_field_handle(ctx, in, out)` | `fuse_field_name` | `fuse_field_ref` | struct form; the name form is below |
| `fuse_register_field(ctx, in, out)` | `fuse_field_view` | `fuse_null` | before `fuse_initialize` |
| `fuse_initialize(ctx, in, out)` | `fuse_null` | `fuse_null` | collective |
| `fuse_is_coupling_ongoing(ctx, in, out)` | `fuse_null` | `fuse_ongoing` | |
| `fuse_begin_step(ctx, in, out)` | `fuse_step_request` | `fuse_step_report` | struct form; the name form is below |
| `fuse_end_step(ctx, in, out)` | `fuse_step_request` | `fuse_step_report` | struct form; the name form is below |
| `fuse_run(ctx, in, out)` | `fuse_run_request` | `fuse_null` | |
| `fuse_view_field(ctx, in, out)` | `fuse_field_ref` | `fuse_field_view` | |

| `fuse_request_restart_point(ctx, in, out)` | `fuse_null` | `fuse_null` | |

### Generic overloads for strings

Five names are generic interfaces with a second, string-taking specific, so you never build a
NUL-terminated `c_ptr` by hand at the common call sites:

```fortran
status = fuse_load_graph(ctx, yaml_path, out)             ! character(len=*) :: yaml_path
status = fuse_field_handle(ctx, component, field, out)    ! character(len=*) :: component, field
status = fuse_begin_step(ctx, component, out)             ! character(len=*) :: component
status = fuse_end_step(ctx, component, out)
status = fuse_last_error(ctx, message, truncated)         ! character(len=*), intent(out) :: message
                                                          ! logical, intent(out), optional :: truncated
```

Each string form trims its argument, appends `c_null_char`, and calls the struct form. The
`fuse_last_error` string form fills `message` with as much of the message as fits (blank-padded) and
reports through `truncated` whether it was cut. The struct forms stay available for callers that
want the raw `fuse_error` members (`length`, `code`) or that keep a `fuse_step_request` across
calls, as `v_loop.f90` does.

### `struct_size`, defaults and arrays

**`struct_size` is set by the module, not by you.** Every `fuse_<entry>` sets `in%struct_size` and
`out%struct_size` from `C_SIZEOF` before making the call. A program compiled against an older
`ffuse` keeps running against a newer `libfuse-abi` for the same reason a C caller does.

**Defaults are default initialisation.** Declaring an argument type and setting only the members
you need passes exactly what a C caller passing a zeroed struct would. Reinitialise a reused
variable with its structure constructor (`out_rep = fuse_step_report()`) rather than relying on the
previous call's contents.

**Arrays** are passed as `c_loc()` of a contiguous `target` (or allocatable `target`) array in
`view%data`, with `count`, `stride` and `component_stride` set explicitly. The array must stay
allocated and at the same address until `fuse_destroy`.

### Type mapping

| In the C header | In Fortran | Note |
|---|---|---|
| argument struct `fuse_x` | `type, bind(C) :: fuse_x`, members in the same order | `C_SIZEOF` equals the C `sizeof` |
| `uint32_t`, `int32_t` | `integer(c_int32_t)` | unsigned members hold values below 2³¹ by construction |
| `int64_t`, `uint64_t` | `integer(c_int64_t)` | |
| any pointer, `char*` | `type(c_ptr)` | `c_loc()` of a `target`; strings NUL-terminated |
| `fuse_exact_time`, `fuse_semantic_version` | `type, bind(C)` of the same name | closed value types |
| `fuse_ctx*` | `type(fuse_ctx)` wrapping one `type(c_ptr)` | opaque |
| function pointers (provider table) | `type(c_funptr)`, set with `ffuse_provider_set_<entry>` | |
| entry `name` | `fuse_name(ctx, in, out)`; link symbol `ffuse_name` | every entry, no exceptions |
| `FUSE_OK`, `FUSE_ERR_*`, `FUSE_ELEMENT_*`, ... | `integer(c_int32_t), parameter` of the same name | |

### Communicators

`fuse_setup_options%communicator` is an `integer(c_int64_t)` holding a Fortran MPI handle. In
Fortran there is nothing to convert: `MPI_COMM_WORLD` (or any communicator from `MPI_Comm_split`)
already is the handle, so `setup%communicator = int(MPI_COMM_WORLD, c_int64_t)`. Also set
`setup%has_communicator = 1`: under Open MPI the handle of `MPI_COMM_WORLD` is `0`, which without
the flag reads as "no communicator". Leave both at their defaults to run with no communicator at
all. To make `fuse_setup` form the base communicator for an MPMD or connect launch, point
`setup%my_component` at a NUL-terminated `target` string; see [Workflow 3](#workflow-3-a-fortran-executable-in-a-multi-executable-coupling).
`fuse_base_communicator` reads the formed handle back, ready for `MPI_Comm_rank` and friends
without conversion.

## Error handling with `fuse_last_error`

Every call returns a status; `FUSE_OK` is `0` and every failure is negative. The message and the
`E-...` code live in the context, not in the status. The `check` subroutine of `consumer.f90`
(included above) is the pattern: on a non-`FUSE_OK` status, call the string form,

```fortran
character(len=512) :: detail
logical :: truncated
status = fuse_last_error(ctx, detail, truncated)
```

and print `trim(detail)`. The message begins with the `E-...` code. For the code alone, or for a
message longer than your buffer, use the struct form: `out%length` is the full length, `out%code` a
`c_ptr` to the NUL-terminated code (valid until the next failing call on this context, and not after
`fuse_destroy`). Passing a default (null) `fuse_ctx` reads the thread-local error of a failed
`fuse_create`. The participant-side codes are listed in [](c-abi.md); `FUSE_ERR_VERSION` from any
call means the module and the library disagree about a struct's layout, which happens only when they
come from different FUSE versions.

## Writing a provider plugin: the `ffuse_provider` module

A provider plugin is the other direction: FUSE owns the loop, loads your shared library from the
`plugin_path` named in the graph, and calls your procedures once per step. The contract (call order,
`describe`/`bind`, the exact-window echo rule, capabilities, restart blobs) is in [](providers.md);
this section is the Fortran mechanics.

`fortran/ffuse_provider.f90` exports:

`type, bind(C) :: fuse_provider_abi_v1`
: The table, bit-for-bit the C layout: `struct_size`, `abi_version`, then one `type(c_funptr)`
  per entry in table order: `version`, `create`, `destroy`, `describe`, `bind`, `advance`,
  `save_state`, `restore_state`, `capabilities`, `save_restart_blob`, `load_restart_blob`. All
  default to `c_null_funptr`.

`ffuse_provider_<entry>_proc`
: One abstract interface per entry, so your own `bind(C)` procedure is checked against the expected
  signature at the setter call. Every one has the shape
  `function f(self, in, out) result(status) bind(C)` with `type(c_ptr), value :: self`, the
  `in` type `intent(in)`, the `out` type `intent(inout)`, and `integer(c_int32_t) :: status`.
  The `in`/`out` types per entry are those of the table in [](providers.md#the-table).

`ffuse_provider_set_<entry>(table, proc)`
: Eleven subroutines, one per entry, that store `c_funloc(proc)` into the table.

`ffuse_provider_bootstrap(table, abi_version)`
: Returns `c_loc(table)` when `abi_version == FUSE_ABI_VERSION`, else `c_null_ptr`. It does not
  fill `struct_size` or `abi_version`; the plugin does, once, before the first call.

The plugin itself must define the one exported symbol, as a top-level function:

```fortran
function fuse_provider_abi(abi_version) result(ptr) bind(C, name="fuse_provider_abi")
```

Its table variable must be `save, target`, because FUSE keeps the pointer for the plugin's lifetime.
`test/abi/plugins/linear_provider.f90` is a complete provider (one `Provides` field, `out`, set to
`t_end` at every advance; the same physics as its C twin `linear_provider.c`, so the conformance
suite can compare the two bit for bit):

```{literalinclude} ../../test/abi/plugins/linear_provider.f90
:language: fortran
:lines: 7-200
```

Inside your procedures, `self` is the `c_ptr` your `create` returned: recover your instance with
`c_f_pointer(self, inst)`. `in%data` of `bind` is likewise a `c_ptr` to storage FUSE owns; map it
with `c_f_pointer(in%data, array, [in%count])` and keep the pointer for `advance`. The plugin is
named in the graph with `launch: {mode: plugin, plugin_path: <path to the .so>}`; see
[](providers.md#naming-your-plugin-in-the-graph).

## Workflows

### Workflow 1: a Fortran code keeps its own time loop and drives FUSE

The participant pattern above. Your program decides when to step; FUSE tells it the exact interval
(`report%t_begin`, `report%t_end`) and makes imports current at `fuse_begin_step`. Nothing in the
program names the partner: the graph does, and the same executable couples to a C partner, a C++
partner, a plugin or another Fortran program depending only on the YAML it loads. `consumer.f90` is
the single-process version; `v_main.f90` is the MPI version. If the graph declares a plugin
component as well, `fuse_initialize` mounts it in your process and FUSE advances it between your
`fuse_begin_step`/`fuse_end_step` calls.

### Workflow 2: a Fortran solver becomes a plugin that a driver in another language runs

Package the solver as a provider plugin (above). The driver is any program that reaches FUSE
through the participant ABI, in C, C++ or Fortran: it loads a graph in which your component says
`launch: {mode: plugin, plugin_path: ...}`, calls `initialize`, and either drives its own component
with `begin_step`/`end_step` while FUSE advances yours in between, or, if it hosts no externally
driven component, calls `run(periods)`. [](providers.md#a-driver-that-runs-plugins) shows such a
driver. The solver never sees the driver's language; the driver never sees Fortran. A Fortran plugin
built with gfortran also exports the compiler's module symbols; see
[](providers.md#a-note-on-exported-symbols).

### Workflow 3: a Fortran executable in a multi-executable coupling

A Fortran participant and a C or C++ participant can be separate executables, either in one MPMD
`mpiexec` or launched independently and joined with MPI connect/accept. The Fortran side does three
things differently from the single-process case: it initialises MPI itself, it passes its own
`MPI_COMM_WORLD` and `my_component` to `fuse_setup`, and every rank calls `fuse_setup`,
`fuse_initialize` and the step calls (`fuse_setup` performs the connect/accept handshake when the
graph says so; `fuse_destroy` disconnects). The graph declares the launch mode per component:

```yaml
components:
  - name: U            # C executable
    ranks: {first: 0, count: 1}
    launch: {mode: mpmd, appnum: 0}
    # fields ...
  - name: V            # Fortran executable
    ranks: {first: 1, count: 1}
    launch: {mode: mpmd, appnum: 1}
    # fields ...
```

or, for independently launched programs,

```yaml
  - name: U
    ranks: {first: 0, count: 1}
    launch: {mode: connect, is_acceptor: true, port_file: brusselator_connect.port}
  - name: V
    ranks: {first: 1, count: 1}
    launch: {mode: connect, is_acceptor: false, port_file: brusselator_connect.port}
```

(`examples/brusselator/participants/reference_mpmd_3.yaml` and `reference_accept_3.yaml` are the
complete files, with a coupler as the third component.) The launch lines, as the test suite runs
them for the Brusselator pair with one rank per program:

```sh
# MPMD: one mpiexec, one ':'-separated segment per executable, in graph order
mpiexec -n 1 brusselator_u_main --graph graph.yaml --log u.log --periods 2 \
    : -n 1 brusselator_v_main --graph graph.yaml --log v.log --periods 2 --ranks-u 1 --ranks-v 1 \
    : -n 1 brusselator_coupler_main --graph graph.yaml

# connect: two mpiexec invocations, the acceptor first and backgrounded
mpiexec -n 2 brusselator_u_main --graph graph.yaml --log u.log --ranks-u 1 --periods 2 &
mpiexec -n 1 brusselator_v_main --graph graph.yaml --log v.log --periods 2 &
wait
```

The two sides' `--periods` must agree, because every rank must step the same number of periods.
[](multiple-executables.md) has the layout rules, the C++ `connect()` API, the error codes and the
build requirement for connect/accept.

### Workflow 4: a graph-driven driver controlled from the command line

The Brusselator participants are the pattern for a reusable Fortran driver, even though their physics
is fixed. Nothing about the coupling is in the programs: `brusselator_graph_tool` (a small C++
program) writes the YAML for a requested layout,

```sh
brusselator_graph_tool --ranks-u N --ranks-v N [--ranks-coupler N] --launch mpmd|accept \
    --out graph.yaml [--port-file path] [--transport fuse|lowfive]
```

and `v_main.f90` takes `--graph graph.yaml`, `--log v.log`, `--periods N`, `--ranks-u N`,
`--ranks-v N`, `--transport fuse|lowfive` and `--solver ...`. Rank counts, launch mode, windows,
iteration regions and remap settings change in the YAML; the executable is rebuilt only when the
physics changes. To reuse the pattern for your own code:

1. Keep the graph in YAML, written by hand, by a C++ tool, or by Python
   ([](python.md) loads, validates and writes the same files). Your driver only loads it.
2. Take the graph path, this executable's component name and the period count (or an end time
   for `fuse_setup`) from the command line, and pass the name as `my_component`.
3. Resolve every field by name with `fuse_field_handle`, size storage from your own
   decomposition, and register it. `fuse_field_handle` works for any component in the graph, so
   the driver can also learn the handles of the peer's fields.
4. Loop on `v_loop_step`'s shape until `next_component == -1`, once per period.

There is no shipped generic driver executable: the Brusselator programs are examples with fixed
physics. See [](drivers.md) for the C++ side of the same question and [](yaml.md) for the file
format.

## Limitations

- The participant limits in [](c-abi.md#limitations) apply: only `FUSE_ELEMENT_F64` fields in host
  memory, no `FUSE_OWNERSHIP_GHOSTED`, one open step per context, no restart file from the
  participant side.
- A Fortran participant links two ABI libraries (`fuse::abi-fortran` and the shared `fuse::abi`);
  `fuse::abi-static` does not link for an installed consumer.
- The consumer project must enable the CXX language and find `Threads`, as shown above.
- A Fortran provider plugin built with gfortran also exports compiler-mangled module symbols; see
  [](providers.md#a-note-on-exported-symbols).
- `service_name` connect targets and the other launch limits of [](multiple-executables.md) apply
  unchanged.
